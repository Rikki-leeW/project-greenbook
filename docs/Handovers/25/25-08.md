SPRIG APP DEVELOPMENT CONTINUITY BRIEF — LATE AUGUST 2026

Treat this as a direct continuation of the existing Sprig development project. Do not restart the design process, rename concepts, replace established architecture, or invent a different roadmap unless Rikki specifically asks.

Sprig is a React + TypeScript + Vite PWA, repository project-greenbook, branch master, deployed with GitHub Pages. Data currently lives in localStorage; there is no backend/cloud database yet.

Sprig is not a conventional gardening tracker. It is a woodland garden chronicle, inspired by an old gardener’s notebook. It should feel elegant, timeless, botanical, tactile, gently magical, warm, practical for serious gardeners, and never childish or cluttered.

Core design principle:

“Purpose determines presentation.”

Pages are for reading. Cards are for decisions. Tags show selections rather than every possible choice. Large collections should read like notebook indexes rather than walls of cards. Parchment remembers choices; notebook pages tell the story.

CONNECTED RECORD NAVIGATION — RECENTLY COMPLETED AND THOROUGHLY TESTED

A major recent architectural pivot was making saved records genuinely traversable.

Rule:

If Sprig displays a saved linked record, the gardener should be able to open it.

Recent work established contextual navigation in the Library:

Growing Recipe → Product → Product Detail
Growing Recipe → Ingredient → Ingredient Detail
Ingredient → Growing Recipe
Linked Growing Recipes can be opened

Detail pages can have two kinds of return action:

Contextual return, for example
← Back to My Potato Mix
Permanent shelf return, for example
← Products

If the record was opened directly from its own shelf, only the shelf return should appear.

AppLibrary.tsx now contains navigationOrigin state to support this.

RecordActions.tsx is the shared record action component and now supports:

contextual back label/action
normal back
edit
duplicate/variation
rate
favourite
archive
restore
delete

This architecture has been thoroughly browser-tested, including editing recipes, adding ingredients, moving repeatedly between Recipes, Products and Ingredients, and returning through contextual navigation.

MAIN ROADMAP / WHERE WE WERE BEFORE THE RECENT SIDE QUESTS

Do not let the photo task become the new roadmap.

The larger development conversation had moved into deeper app architecture and infrastructure, including:

1. Data safety / Backup & Export

This is important because Sprig currently relies on localStorage and is becoming a real everyday garden record.

Satchel already contains a planned Backup & Export destination described as important before Sprig becomes the gardener’s everyday record.

This broader branch should include thinking about:

whole-garden backup
restore/import safety
versioning/migrations as the data model evolves
human-readable exports where useful
protecting historical records

Plant Story already has an individual JSON export implementation, so export is not an entirely new concept.

2. Library exporters / comparison tools

We had begun discussing the Library becoming useful not only as storage, but for comparing records over time.

Important future examples include:

compare plants of the same crop/variety
compare timing
compare Growing Places
compare Growing Recipes
compare products / costs
eventually export comparison data

This is especially important for real gardening questions such as why one broccoli forms a head while another same-age plant does not, or why one potato bag succeeds while another fails.

Do not flatten this into generic analytics. Sprig should surface garden stories and useful comparisons.

3. Calendar architecture

We had been discussing a real Sprig calendar/timeline layer.

Dated records already exist across Plant Stories, Garden Events, Harvests, purchases and expected harvest timing.

The newer harvestTimingReference architecture deliberately gives future Calendar features stable links to real dated garden milestones.

The Calendar should eventually be able to understand:

sowing
planting out
transplant events
garden activities
harvest expectations/windows
actual harvests
purchases where relevant
future reminders/tasks if introduced

Avoid inventing duplicate date systems when existing records can feed the Calendar.

4. App-level state / navigation architecture

This was becoming important because Sprig is outgrowing ad-hoc page-level selections.

Current App.tsx already controls central selected records and navigation for:

Plant
Journal Event
Harvest
Growing Place
Library destinations

AppLibrary.tsx has its own internal detail/navigation state.

We had been discussing whether some of this should eventually become cleaner shared app-level state rather than continuing to bolt more selected-record variables onto App.tsx.

Do not prematurely introduce Redux/Zustand/etc merely because the app is growing. First understand the actual state/navigation pressure and choose the smallest architecture that solves it.

5. Financials / “Accountant Sprig” later

PurchaseRecord is intentionally laying groundwork for deeper cost intelligence.

Future work includes:

seed/seedling purchases
products
ingredients
Growing Mix inputs
quantity/package pricing
supplier history
allocations of a purchased product across plants/recipes/places
cost per crop / harvest / growing experiment where meaningful

This is later work. Do not turn Sprig into accounting software prematurely.

6. Styling / design refinement later

Much of the current UI is functional scaffolding.

Styling matters, but the development strategy has generally been:

architecture and behaviour first → styling pass later

Exceptions are usability problems that genuinely interfere with use, such as enormous photographs, inaccessible buttons, unreadable forms, or broken mobile layouts.

Do not spend hours polishing button shadows while core architecture is unfinished.
